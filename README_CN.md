7# Flowbit v2 —— 种子式基础分发与边缘计算架构

> 前身为 BCST-DT（基于目录的压缩切片隧道差分传输）。
> v2 在保留"服务端不依赖用户 P2P"核心原则的前提下，
> 将架构从"极限压缩+固定切片"重构为"种子式底包+按需拉取+边缘多功能节点"。

---

## 设计哲学

Flowbit v2 的核心隐喻仍然是泉水：

泉水不一次性涌出整片湖，而是持续、按需、低阻力地渗出。
底包不是"全部游戏文件的压缩包"，而是能进游戏的门票——也就是种子文件。
进了门之后，剩余资源从边缘节点按需拉取。
开发者不需要自建昂贵的 CDN，不需要用户参与 P2P 共享。
隧道节点既是文件缓存，也是联机中转——一台服务器干两件事，利用率拉满。

## 三角约束

| 维度 | v2 的做法 |
|------|-----------|
| 体积 | 源头减少（SVG 替换 + shared_lib 去重），不靠极限压缩硬挤 |
| 速度 | 分类包小粒度 + 不压/轻压，解压时间趋近于零；HTTPS 传输快 |
| 兼容性 | 纯 HTTPS + 标准 tar + 可选 zstd，客户端零特殊依赖 |

## 目标一：种子式底包 —— 能进游戏就够

**一代做法：** 把所有文件 tar 后 7z LZMA2 极限压缩，切成 50MB 切片，客户端全量下载解压。

**v2 做法：** 底包只含"能启动游戏的最小集"，体积控制在 50-100MB。它本质上是一个种子文件——包含隧道节点地址表和资源清单，但不包含全部游戏资源。

底包内容：

| 内容 | 说明 |
|------|------|
| 游戏引擎/运行时 | 必须，进游戏用 |
| 核心脚本/配置 | 启动必需 |
| 基础 UI（SVG） | 极小 |
| starter_content/ | 1-2 个初始场景/角色，够看画面 |
| shared_lib/ | 公共文件库（去重后的通用资源） |
| tunnel_nodes.json | 隧道节点地址列表（多节点，带优先级和地区） |
| resource_manifest.json | 完整资源清单（路径+哈希+大小+分类+priority） |

底包一旦发布永不修改。所有后续变化通过补丁和分类包增量叠加。

## 目标二：公开文件库（shared_lib）—— 从源头去重

**一代做法：** 每个目录各自存文件，更新时整个切片重下。

**v2 做法：** 扫描所有目录，找出字节级完全相同的文件，提取到 shared_lib/ 目录。原位置留下 .ref 指针文件，内容为一行路径，指向 shared_lib 里的实际文件。

| 对比 | 一代 | v2 |
|------|------|----|
| 同一个按钮图标出现在 8 个目录 | 存 8 份 | 存 1 份 + 8 个指针 |
| 改了这个图标 | 8 个目录各自更新 | 只更新 shared_lib 里 1 个文件 |
| 客户端下载 | 下载 8 份 | 下载 1 份，所有引用共享 |

指针文件示例：

文件名：ui/buttons/confirm.png.ref
文件内容：shared_lib/btn_confirm.webp

manifest 中标记为 type: "ref"，客户端读到后自动去 shared_lib 路径拉取。

## 目标三：分类归档 + 不二次压缩

**一代做法：** 全部文件 tar 成一个流，7z LZMA2 极限压缩。

**v2 做法：** 按类型/主题把文件归档到文件夹，然后对每个文件夹分别处理：

| 分类 | 处理方式 | 原因 |
|------|----------|------|
| base/（代码、配置、bin/data） | tar.xz，LZMA2 极限压缩 | 高度可压缩，字典命中率高 |
| characters/（人物模型+贴图） | tar.xz，LZMA2 极限压缩 | 同类文件打包后跨文件有冗余可吃 |
| costumes/（服装贴图） | tar.xz，LZMA2 极限压缩 | 同上 |
| ui_textures/（UI 贴图） | tar.xz，LZMA2 极限压缩 | 同上 |
| audio_bgm/（背景音乐） | tar.zst，store 模式 | 已压缩音频再压无意义，只归档不解压 |
| videos/（视频） | tar.zst，store 模式 | 已压缩视频再压无意义 |
| 活动文件（event_xx/） | 不压缩，直接放文件 | 短命资源，不值得花 CPU 压缩和解压 |

关键原则：绝不重复压缩。每个文件只经过一次压缩（或完全不压）。已压缩格式（WebP/PNG/JPG/MP3/MP4）直接 store 模式归档。

## 目标四：隧道节点 —— 从 BT 网格到 HTTPS 边缘节点

**一代做法：** 隧道节点运行 BT 客户端，预推送切片，用户从节点拉取。

**v2 做法：** 隧道节点退化为标准 HTTPS 文件服务器 + 联机中转。支持两种同步模式：

| 模式 | 说明 |
|------|------|
| 懒缓存（推荐起步） | 客户端请求 → 节点没有 → 回源拉 → 缓存 → 返回 |
| 主动同步（规模期） | 源服务器推送新版本到节点，节点间可互相同步 |

节点存储策略：

| 数据类型 | 存储位置 | 淘汰策略 |
|----------|----------|----------|
| 底包 + shared_lib | NVMe 热缓存，永久保留 | 不淘汰 |
| 当前活动文件 | NVMe 热缓存 | 活动结束 del-patch 删除 |
| 旧分类包/旧活动 | HDD 温缓存 | LRU，30 天未访问自动删 |
| 已标记 tombstone 的文件 | 任意 | 超过 7 天物理删除 |

节点本身用 nginx + 自签或 Let's Encrypt 证书提供 HTTPS 服务。不需要 BT 客户端，不需要特殊协议。

## 目标五：补丁与活动生命周期 —— 增量叠加 + 安全删除

**一代做法：** bsdiff 生成差量，达到阈值合并，del-patch 删除过期文件。

**v2 做法：**

补丁策略：

| 补丁类型 | 处理方式 | 放哪 |
|----------|----------|------|
| 配置/文本修改 | 单独 patch 文件 | patches/patch_xxx.json |
| 单个小文件替换 | 单独 patch 文件 | patches/patch_xxx.bin |
| 代码/逻辑热更 | 单独 patch 文件 | patches/patch_xxx.script |
| 多个文件批量改 | 重新打分类包 | characters_v1.2.tar.xz |
| 活动上线 | 整个活动目录推到节点 | events/event_xx/ |
| 活动下线 | del-patch 指令 | del_patches/del_xxx.json |

删除流程（核心安全机制）：

| 步骤 | 执行者 | 说明 |
|------|--------|------|
| 1. 文件标记为 deprecated | 系统自动 | 活动结束或补丁被覆盖时触发 |
| 2. 沙箱验证 | 自动化 | 内置客户端（内测服）启动游戏，验证删除后能否正常运行 |
| 3. AI 分析建议 | AI 辅助 | 扫描依赖关系，输出建议报告（不执行删除） |
| 4. 人工确认 | 测试人员 | 查看 AI 报告 + 沙箱结果，手动批准或拒绝 |
| 5. del-patch 下发 | 系统 | 客户端+隧道节点同步删除 |
| 6. 回滚窗口 | 系统 | 保留 7 天，期间可撤销 |
| 7. 源服务器归档 | 系统 | 移到冷存储 |
| 8. 最终删除 | 人工/定期 | 确认永远不需要后清理 |

AI 只提供建议，没有超级用户权限，不能主动清理文件。

## 安全与传输规范

所有节点间及节点到客户端的通信必须通过 HTTPS（TLS 1.3）。不允许明文 HTTP。

| 项目 | 建议 |
|------|------|
| 证书类型 | Let's Encrypt 免费证书起步 |
| 进阶建议 | 有能力请购买商业 CA 证书并完成 ICP 备案（面向国内用户） |
| 备案好处 | 更稳定的 TLS 握手、避免运营商劫持、老旧设备兼容性更好 |
| 应用层加密 | 可选 AES-256-GCM，源服务器加密 → 客户端解密，节点只存密文 |
| manifest 签名 | Ed25519 私钥签名，客户端验证签名后再信任内容 |
| 文件校验 | 每个文件附带 SHA-256，客户端下载后验证 |

## 传输性能优化

| 优化项 | 做法 | 效果 |
|--------|------|------|
| HTTP/2 | nginx 开启 http2 | 多路复用，延迟降 30-50% |
| Brotli 预压缩 | 构建时生成 .br 文件，nginx 直接发 | manifest/JSON 体积减 70-80% |
| Cache-Control | 分类包设 max-age=31536000, immutable | 客户端二次启动不重复请求 |
| TCP BBR | 内核开启 BBR 拥塞控制 | 跨地区同步快 2-5 倍 |
| Range 请求 | nginx 原生支持 | 断点续传，弱网下不重下 |
| 节点间同步 | rsync + SSH | 只传差异部分，断点续传 |

## 功耗与能耗压缩

### 硬件层面

| 手段 | 效果 |
|------|------|
| 选用 ARM 架构节点 | 功耗从 ~25W 降到 4-6W |
| 内存双通道（2 根条） | 带宽翻倍，TLS 吞吐更高，同时服务更多连接 |
| HDD 休眠 | 无访问 5 分钟后 0 转 |
| NVMe ASPM 电源管理 | 空闲时进入 L1.2 低功耗状态 |
| CPU 频率调节 | 空闲时 powersave 模式，功耗砍半 |
| 无头运行 | 不接显示器，SSH 管理，省 GPU 功耗 |

### 软件层面

| 手段 | 效果 |
|------|------|
| nginx worker = CPU 核数 | 不浪费空转 |
| TLS 会话复用 | 减少握手 CPU 消耗 |
| 限流+排队 | 防止突发流量打满 CPU |
| 构建任务错峰 | 凌晨 3-5 点跑压缩 |
| 客户端请求合并 | 每 5 秒合并一次待下载列表，减少连接数 |

### 实际电费估算（自托管，3 节点+1 源服）

| 设备 | 日均功耗 | 月电费（¥0.6/kWh） |
|------|----------|-------------------|
| 源服务器 | ~1.2 kWh | ~¥22 |
| 3× ARM 隧道节点 | ~0.15 kWh/台 | ~¥8/台 |

## 成本控制

| 策略 | 做法 |
|------|------|
| 隧道节点自动启停 | 流量低于阈值自动关机，高于阈值自动拉起（云厂商按量实例） |
| 冷存储归档 | 源服务器上 30 天未访问的文件移到对象存储低频层（几元/TB/月） |
| 局域网客户端互传 | 客户端 mDNS 发现邻居，同一局域网内已下载的资源直接从邻居拿 |
| 回滚窗口 | del-patch 后保留 7 天，确认无异常才最终删除，避免误删后重新分发 |
| 源服务器兜底 | 平时不出流量，所有请求走隧道节点；节点全挂时才回源 |

## 联机扩展（边缘节点多功能化）

隧道节点不只做文件分发，同时承担联机中转和算力溢出：

| 能力 | 说明 | 何时启用 |
|------|------|----------|
| 文件服务 | HTTPS 文件缓存和分发 | 始终在线，低优先级 |
| 联机中转 | 客户端 ↔ 隧道 ↔ 主服务器，转发游戏状态同步包 | 用户联机时 |
| 房间托管溢出 | 主服务器负载高时，对局房间分配到隧道节点上跑（Docker 容器） | 主服务器 CPU>70% 或内存>80% |
| 节点间直连 | UDP 打洞辅助，两个客户端尽量直连，节点只在打洞失败时中继 | 大规模并发时 |

主服务器只管匹配和全局状态，对局数据走隧道节点间直传。Docker cgroups 确保文件服务和联机进程资源隔离，互不抢占。

## 已知局限

| 局限 | 说明 |
|------|------|
| 底包不含全部资源 | 首次进游戏后需要后台下载，弱网用户体验受影响 |
| 隧道节点需要公网 IP | 每台节点仍需一个可达地址（可用内网穿透替代，但增加延迟） |
| 联机溢出增加复杂度 | 房间逻辑需要在主服务器和节点间同步状态，开发工作量上升 |
| 不兼容一代客户端 | v2 协议与一代不兼容，需要客户端重新实现 |
| 已压缩媒体无法再压 | 视频/音频/WebP 只能 store 模式，体积比极限压缩大 |
